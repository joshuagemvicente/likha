## Overview

Lisa is a terminal coding agent for one person working in one repository at a time. The v1 workflow is: select a repository, connect to a hosted provider from the predefined accepted list with a user-supplied API key (BYOK), ask for a change, inspect a proposed diff, approve or reject it, review each proposed command, then resume the conversation after exiting. The provider receives the content Lisa sends it; approving a shell command does not sandbox that command. Lisa hosts no models and bundles no local inference server; it needs no service of its own.

Use **ultrathink** as a working mindset: trace each user-visible action from request through approval, persistence, interruption, and recovery before calling a feature complete. Keep the implementation small enough to reason about. Require a real terminal smoke scenario in addition to tests, especially where a crash, a narrow viewport, or a stale edit could change the outcome.

This setup and delivery plan records the local SQLite and macOS ARM64 protocol-server smoke checks in [feature-test-plan.md](feature-test-plan.md). The published-binary walkthrough and the hosted BYOK providers in [predefined-providers/](predefined-providers/spec.md) remain open. [v1-spec.md](v1-spec.md) defines the product contract.

## Architecture

- Use Go 1.24 and the existing `cmd/lisa` entry point. Keep the Bubble Tea/Lip Gloss full-screen view in `internal/app`; the app coordinates the model client, repository tools, reviewed actions, and session store. Avoid another service or plugin layer.
- Select the repository before opening its session. Resolve its canonical directory path so a relative path and a symlink to the same directory share history, while a different directory cannot load that history. Repository read/write tools still validate resolved paths independently; the database does not authorize filesystem access.
- Let `internal/model` stream assistant text and structured tool calls from the configured provider — one OpenAI-compatible surface; hosted providers differ only by base URL, auth header, and session-routing headers from the predefined list. Reject unsupported tool-call behavior rather than interpreting assistant prose as commands.
- Route proposed edits through a displayed diff and explicit decision. Check for a stale file before applying an approved edit. Show the exact command and working directory before command approval, then report actual output and exit status. A saved session must contain completed outcomes, not a permission to replay an interrupted proposal.
- Let `internal/session` own local SQLite persistence behind the existing create/list/load/save flow, including opening and closing the database. Keep configuration and session files outside the selected repository so they do not enter commits by accident.

## Database Setup (SQLite)

1. **Choose the local state directory.** Use `LISA_STATE_DIR` if set; otherwise use the operating system's user configuration directory with a `lisa` child (on macOS this is normally `~/Library/Application Support/lisa`; on Linux use `$XDG_CONFIG_HOME/lisa` when set, otherwise `~/.config/lisa`). Resolve the chosen directory before launch. Keep it private to the user (directory mode `0700`) and avoid storing the database under the repository. Backups inherit the same sensitivity as prompts, diffs, and tool output.
2. **Open one database.** Put `sessions.sqlite` in that directory with mode `0600`; keep its `-wal` and `-shm` sidecars in the same private directory. Use a local SQLite driver in the Go application; no cloud database or database daemon is required. Report inaccessible or corrupt state as an actionable storage error rather than silently starting an empty history.
3. **Set connection behavior.** Enable WAL journaling, a 5-second busy timeout, `synchronous=FULL`, and foreign-key enforcement on connections. Keep writes transactional. Verify that another local connection sees only committed snapshots and that an interrupted transaction does not masquerade as a completed action. Close the store during normal exit so callers do not leave a live connection behind.
4. **Version the schema.** Start with SQLite `user_version=1`. Store sessions with an identifier, canonical repository path, last-update time, a list title, and the saved conversation snapshot; index by repository and update time for the session picker. Initialize version 1 only when opening a genuinely empty unversioned database. Reject an unknown nonempty unversioned database or a future version without overwriting it. For each later schema change, specify a numbered transactional migration and a rollback/restore path before shipping; do not claim that older per-session JSON files migrate automatically. Preserve those legacy files separately if a user needs to recover them.
5. **Back up and restore safely.** Before upgrades or manual cleanup, use SQLite's online backup operation (for example the `sqlite3` CLI `.backup` command) to produce a consistent copy in a private location. Do not copy only `sessions.sqlite` while WAL may contain uncheckpointed commits. To test a restore, close Lisa, place the backed-up database into a separate private state directory, point `LISA_STATE_DIR` at it, and list/resume a known session for its repository. Keep backup retention under user control and remove an old backup only after checking the restored copy.
6. **Check the actual state path.** Launch Lisa once for a sample repository, confirm the private database location and permissions, create a completed conversation, exit, then list and resume it. Try another repository and a relaunch interrupted at an approval prompt; neither should expose or execute the first repository's pending proposal. Run the Feature 4 tests and smoke gate before calling persistence verified.

## Design & Aesthetic Guidelines (“good taste”)

- **Layout:** Use the alternate screen and occupy the viewport with a fixed header, one content area, and a status/control footer. Do not scroll the terminal or a pane. Paginate conversation, diffs, and command output with visible `Page n/m` position and previous/next controls; never silently clip large results. Preserve the user's page while new text streams unless the user chooses the newest page.
- **Priority:** During a review, show affected paths and the proposed diff, or the exact command and working directory, above branding. Keep approval and rejection labels visible on every review page. Require access to every diff page before allowing edit approval; rejection and cancellation remain available without paging through the proposal. Do not make a color or highlight the only cue that an action needs consent.
- **Keyboard clarity:** Label the actual keys in the footer (`Y` approve after review, `N` reject, `PgUp`/`PgDn` pages, `Ctrl+C` cancel, `Ctrl+D` quit where available). Keep prompt entry distinct from review decisions. Explain when approval is blocked by unseen pages, a stale edit, or an undersized terminal; never let an unlabeled shortcut authorize a write.
- **Visual restraint:** Start with readable terminal defaults. If color is available, reserve one calm accent for focus, one warning treatment for a pending review, and one error treatment; avoid heavy borders, gradients, or colored log floods. Pair each state with text such as `Waiting for model`, `Review edit`, `Rejected`, or `Session save failed`. Use sufficient foreground/background contrast in both light and dark terminals; verify with color disabled and a monochrome terminal.
- **Identity and width:** Keep Lisa's existing plain ASCII logo at comfortable sizes. On narrow or short terminals, replace it with a compact `Lisa` header before sacrificing repository identity, page position, or approval controls. Reflow text and diff lines at terminal width while keeping file paths and change markers legible. At dimensions too small for safe approval, request a resize and disable approval instead of clipping the decision.
- **Large output and errors:** Treat long model responses, tool results, and command output as paged content in the same frame, not writes to terminal scrollback. Mark intentional result limits explicitly so users do not mistake truncation for a complete result. Give model, storage, path, stale-edit, command, and cancellation outcomes distinct readable messages and a route back to a prompt or normal exit. Restore the terminal screen on exit.
